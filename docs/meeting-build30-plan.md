# build 30：证据表达与最小修订

日期：2026-10-31。继续录音开发分支和待合并 PR，不修改 B 站、ASR、云模型或新任务默认策略。

## 上轮结果与本轮取舍

build 29 的同一真实录音，草稿 20/33、核验后 22/33，禁止错误检查 3/5。历史全文基线也是 22/33，但不是同构建同预算的同期实验。主要失败是将不同资源合成一个待交付事项、把单方安排变为决定，以及核验时替换整条造成细节丢失。单轮数字不是整体准确率。

本轮保持全文草稿、独立证据、对照修订三阶段；不增加 agent、检索服务或新的模型请求阶段：

1. 独立证据只要求一项事实或关系及原文来源，不再套用面向最终纪要的行动、负责人、状态标签结构。不同对象或状态分开，条件与被限定事项一起保存。
2. 用与验收录音无关的少量通用例子，明确已有资源/待发新版本、个人做法/单方建议/共同决定、条件/期限及口述矛盾。例子不作为生成事实来源。
3. 新核验请求使用字段级 `update`，程序保留未修改字段；只允许目标类型的白名单字段，仍验证合成后的完整声明和引用。旧 `replace` 诊断兼容；正文内部的语义保留仍需评阅，不能宣称程序已保证事实正确。
4. 审查先核对原文与清单，再检查遗漏及修订副作用。保持原有有界重试、恢复、来源跳转和费用账本。
5. 核验可补回独立清单也漏掉的原文事实，不再强制每个补充绑定清单 ID；仍须引用本批负责原文的有效来源，避免长文各批重复补充邻接背景。

## 依据与适配边界

- [Omi 纪要规则](https://github.com/BasedHardware/omi/blob/f60de9b011ec70cfcab05fde0a6c2669a652ab02/backend/utils/llm/notes_agent_prompt.py)：保持提议、决定、意图和已完成事项的差别，不因语句邻接把细节挂到错误对象。
- [LangExtract](https://github.com/google/langextract)：用少量具体示例约束提取并锚定原文。本轮沿用自有来源编号，不引入其运行库或多遍提取；示例泄漏也必须列入检查。
- [RARR](https://aclanthology.org/2023.acl-long.910/)：修正无依据内容时尽量保留原有内容。本轮只借鉴最小编辑原则，证据来自录音原文，不加入网页检索，不声称复现论文结果。

## 固定验收范围

先完成合成小样本的离线契约、来源、字段修订、失败恢复和旧格式回归，再构建安装。真实付费验收仅通过安装副本界面创建并启动：

- 同一完整版 Large-v3 原稿、说话人信息、同一冻结的 33 项保留和 5 项禁止错误清单。
- 新版 `meeting-v3` 一次、同版 `meeting-baseline` 一次，均使用同一草稿提示词和高思考强度。
- 初始输出 131,072，耗尽仅一次扩至 262,144；沿用既有格式/网络重试和请求总限。开始前另存代码、应用、提示词、输入、清单哈希和完整限制。
- 不重跑 ASR，不调用可选标点，不恢复之前暂停的付费任务，不增加其他大样本或重复次数。任一失败后保留原因和用量，另一项仍可独立完成。
- 一轮开始后不改实现、参数或清单。两项完成或明确失败后统一评阅，分别公开关键错误、遗漏、修订收益/退步、耗时与全部已知用量。

本轮是单轮开发验收，不替代原计划的重复稳定性和多样本门槛。即使单次达标，也不自行切换新任务默认。完成后原位保留一个最新预览应用、一份上一版回退包，更新报告与 PR，等待用户决定后续版本。
