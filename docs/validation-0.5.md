# 0.5 总结流程验收

日期：2026-10-25。模型均为积算平台 `deepseek-v4.1-flash`，推理设置 `low`。同一视频的新旧流程读取相同 SHA-256 的冻结原稿；本轮不重复下载或转录，不把 ASR 改动混进总结质量比较。原始应用任务保留。

## 范围与测量方法

三份原稿分别是 7:10 的 AI 资讯（平台字幕）、55:43 的张仲景视频（本地 Whisper）和 87:05 的 Transformer 论文精读（本地 Whisper）。短稿 192 段字幕、2,652 字；两个长稿分别 1,737 / 2,323 段字幕、12,988 / 28,161 字。

旧引擎在开发前冻结到独立目录，保留原分块、接缝合并、分层汇总及提示词。新版采用紧凑输入、整体阅读或全文规划、完整引用核验与定向回读。每个结果使用独立的检查点目录。模型响应具有随机性，本轮每个方案每份样本只有一次最终完整运行，不是统计显著性实验。

最终计时从空本地检查点开始，不含下载与转录，包含 API 请求、结构校验和实际重试。供应商 Prompt Cache 不受本机控制，独立列出其报告量。两份最终长视频在独立进程同时测试，各自最多两个章节请求并行，因此耗时仍受平台负载影响。开发中的失败、取消和方案迭代另列，不混入最终基准。

## 内容审阅

预先固定了 [67 项内容清单](research-data/summary-quality-rubric-0.5.json)：短稿 15 项、历史 24 项、技术 28 项，包括中段细节、结尾限制、数字、比较方向和后文更正。关键词只用于定位候选证据，实际判定需对照原稿和输出；本轮由开发助手审阅，未进行独立人工盲评，也不等同于外部事实核查。

逐项定位这67个主题，并重点核对数字、条件、跨章更正和结尾限定；未发现清单中的整项主题完全消失。这个结论只针对该清单，不能推广为零遗漏。[逐项审阅记录](research-data/summary-quality-review-0.5.json)公开版保留新版声明编号、旧版候选章节定位与审阅结论，另列9项限定或表达问题；原稿和输出正文保留在本机，不随源码分发。

新版的实际改进：

- 短稿把散落的23条整理为4个自然主题；旧版将某登录代理的支持列表并到HUD数据市场，新版按整稿上下文放回对应产品。
- 历史稿将前文成书年代与末尾205年前后的校订关联，也明确保留“父名材料晚出，作者删去其名”。旧版虽包含校订章，但某些更正未与前文整合、识别字较难读。
- 技术稿把182个小节组织为14章，保留Q/K/V来源、两次矩阵乘法、LayerNorm与BatchNorm区别、n²d和nd²的比较方向、warmup4000，以及末尾“MLP与残差不可少”的限定。概览也带上结尾限制。

尚未稳定胜过旧版的地方，明确保留为本版局限：

- 历史稿某条尾注写“大疫十年十次”，前文及同条日期却是119—217年；这是局部数字措辞冲突，不能因主题已覆盖就判正确。
- 墓碑校订原稿没有清楚标点：旧版断言“刻于330年”，新版断言“并非刻于330年”；两者都没有可靠消除原句否定范围的歧义。
- 技术稿保留4.5万句数据和label smoothing中0.1/0.9的来源数字，没有擅自改为外部知识。但旧版明确把label smoothing数字列为疑点，新版这次漏了该提醒；新版在此项退步。
- 新版保留了embedding/位置编码缩放对象的待核对项，正文解释仍较确定。相似疑问有重复，历史稿22项、技术稿17项，待核对区尚不够精炼。
- 两版都有不处处显式标注“讲述者称”的句子；主题笔记仍较详细，后续需要在忠实度与阅读压缩之间继续评估。

因此，本轮证据支持“长稿组织更连贯、两份长稿更省时省量”，不支持“所有内容质量都已超过旧版”。原稿/精简稿/学习笔记和旧版对照均保留，用户可按时间来源回看。上述语义局限没有通过手工修改模型输出掩盖。

原稿质量仍是上限。历史视频有“正史无载/正是五载”、医名药名和无标点校订句等识别歧义；技术视频口述出现数据集规模、label smoothing 数值和缩放对象的疑点。新版不查询外部资料来静默纠正它们。原稿、精简稿和笔记需要一起回看；编号覆盖不能证明语义零遗漏。

## 发现的问题与修复

1. **推理 Tokens 耗尽输出预算。** 短稿核验曾消耗全部 8,192 输出 Tokens 而没有正式答案；合并整份概览重写也曾触发 16,384 上限。截断结果被拒绝，未写成成功笔记。短稿改为只返回修改项；核验有一次较大预算回退，超限记录可恢复。
2. **跨章来源不全导致误报警。** 一条笔记引用前文与结尾校订，核验只看当前窗口时会把“没看到”误当“原文缺失”。核验改为携带声明的全部引用，同时限制遗漏补充只针对本次负责的原文，减少重复笔记。
3. **回读再次执行整章审查。** 重复审查放大推理开销；改为只回答指定问题，共用来源的问题合并，最多两轮、六次。
4. **概览压缩丢失核验疑问。** 引入有来源的疑问解决记录。未明确解决的疑问不会因概览条数限制消失；定向回读后仍然存在的原文歧义受程序保护，不能由概览再次改写后声称已经消除。
5. **恢复时重复尝试已知过小预算。** 记录明确的输出/上下文超限，并可从已落盘用量日志恢复超限状态。恢复时跳过同一个失败预算，直接使用更大预算的检查点；旧版也可从日志跳过已知超限父请求，直接恢复较小子块。
6. **对照结果难区分。** 新旧流程另建任务，列表显示总结方式；知识点分别提供连续来源时间入口，跨章引用不合成一条横跨全片的链接。

## 中断恢复与数据完整性

对开发验证中的长视频发送真实 SIGTERM：历史视频在全文结构和首章完成后取消，退出耗时 0.058 秒；技术视频分别在章节阶段、完成四轮核验后取消，退出耗时 0.048 / 0.028 秒。恢复后对应 2 / 6 / 19 个检查点的字节哈希和修改时间均保持不变，完成的计算可复用。

取消时的在途请求可能已经由供应商处理。没有返回用量的请求保留“未知”，不能声称取消没有费用。API 用量与本地检查点命中是不同概念。

最终三份新版结果在禁用所有HTTP请求的条件下重放，分别复用2 / 23 / 29个成功检查点，历史稿另复用1个超限记录，全部0请求、0新增Tokens。此重放应用了最后的本地疑问保留规则，不重新调用模型；完整首次计时保存在cold-summary-run.json及benchmark.json中。

实际应用worker对六个导入任务逐一恢复，耗时0.075–0.123秒，全部完成，账本新增HTTP尝试为0。验证过程中额外发现旧引擎会重发已知超限父请求；修复前产生2次在途尝试，用量未知，已计入开发统计。修复后旧版从用量日志恢复超限状态，直接复用已有子块；冻结的旧版单次基准及模型输出不变。原四个任务的job/request/transcript/notes文件哈希和项目归属保持不变。

程序检查：原文紧凑表示逐字还原、精简稿覆盖所有原字幕编号、引用合法且有序、遗漏检查实际读到每个原文段落。它们是结构完整性检查，不是语义正确率。
