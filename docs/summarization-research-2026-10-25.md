# 视频总结的上下文与工作流调研

调研日期：2026-10-25。对象：VideoDHelper 现有中文字幕／本地转录、积算平台 `deepseek-v4.1-flash`，通常 30 分钟以内，最长约 90 分钟。本文是调研与设计建议，尚未实施新总结流程，也未调用付费模型进行新方案实验。

## 结论与优先级

建议采用**按输入规模选择流程：短稿整体理解；长稿先建立全文结构，再按主题整理，关键结论可回查原文**。

目前最值得解决的不是增加 Agent 数量，而是过小的字节分组、缺少全局语境、摘要反复压缩、以及把来源编号覆盖误当成语义覆盖的问题。分块仍可以作为执行、输出预算和断点恢复的单位；它不应决定视频的知识结构。

优先验证三项改动：

1. 将字幕的存储格式与模型阅读格式分开，依据实际 Token 预算选择全文或分章路径。
2. 长稿生成有原稿依据的全文结构、术语表和更正关系，各章节在共享这些信息的前提下阅读原文。
3. 生成后双向检查：结论是否有原文支持，原文中的关键内容是否在完整笔记里得到保留。仅对发现的问题追加回读。

这些是结合本项目问题提出的设计假设，不能把其他模型、英文图书或 RAG 基准上的成绩当成我们已获得的提升。

## 1. 当前实现的离线审计

检查了 [summary.py](../backend/summary.py) 及已完成任务的原稿。当前流程已有上下文重叠、接缝合并、分层汇总、来源校验和断点恢复，并非简单地拼接各块摘要。它的主要限制如下：

| 位置 | 当前行为 | 对理解和效率的影响 |
| --- | --- | --- |
| `batches()`，256 行；调用，327 行 | 按每条字幕 JSON 的 UTF-8 字节数累加，初始预算 4,500 字节 | 不是 4,500 Tokens；字段名、时间戳、编号都占预算；该预算也不包含完整提示词和前后文 |
| 331–333 行 | 每块带前后各 3 条字幕；局部请求没有视频标题或全文结构 | 三条字幕不等于完整语境，难以处理隔数分钟的指代、定义和更正 |
| 16–20 行 | 每块同时输出精简台词与 2–6 条笔记 | 输入切得越碎，笔记条目越碎；执行块数间接决定了输出结构 |
| 235–253 行 | 逐个接缝检查两条已经生成的笔记 | 能修补邻接问题，但此步没有重新读取原稿，也不覆盖非相邻的关系 |
| 374–383 行 | 超过 18,000 字节的概览输入继续按 6,500 字节分组压缩 | 只压缩概览输入，完整章节仍保留；但概览中的条件、主语和跨章关系可能逐层损失 |
| 192–200、220–223 行 | 检查精简稿编号覆盖，并将引用来源向上继承 | 能检查漏处理、重复和非法引用；不能证明结论忠实，或全部重要意思被保留 |

### 实际样本规模

以下是对现有 `transcript.json` 离线重放当前分组算法的结果。字符数包含英文和标点，不是 Token 数；分组数是初始组数，不是总请求数。

| 样本 | 正文字符 | 原始字幕条数 | 初始分组 | 每组平均正文字符 |
| --- | ---: | ---: | ---: | ---: |
| 约 7 分钟新闻，平台字幕 | 2,652 | 192 | 5 | 530 |
| 55:43 张仲景，本地转录 | 12,988 | 1,737 | 38 | 342 |
| 87:05 Transformer 论文精读，本地转录 | 28,161 | 2,323 | 56 | 503 |
| 同一短新闻，本地转录 | 2,730 | 209 | 5 | 546 |

87 分钟技术视频的原稿正文是 75,996 个 UTF-8 字节；当前内部字幕单元列表序列化后为 250,371 字节。只做无损的阅读格式转换，每行保留 `来源编号 原文`，得到 91,146 字节。时间戳和原始字幕的对应表留在程序中，仍可按编号定位。

这个比较未计算提示词、重叠上下文和输出，也没有使用模型 tokenizer，因此**不能声称节省相同比例的 Tokens、费用或耗时**。它证明当前有大量可去除的传输冗余。

可核查数据及输入／代码 SHA-256：[离线审计 JSON](research-data/summarization-input-audit-2026-10-25.json)。复算步骤：按当前代码将超长字幕拆成最多 700 字符的单元，调用 `batches(units, 4500)`；正文字符和字节分别求和。

已有的 [0.3 验证记录](validation-0.3.md) 还记录过一个直接相关的问题：复杂度比较在压缩后因“前者／后者”指代变化而颠倒。后来用提示词约束和疑点标注修复了该样本，但仅靠保留来源编号无法防止这类错误。

## 2. 论文和工程实践给出的证据

| 方法或问题 | 一手证据 | 对本项目的含义与边界 |
| --- | --- | --- |
| 分层摘要并非无效 | [SummN，ACL 2022](https://aclanthology.org/2022.acl-long.112/) 在长会议、对话和文档上验证了多阶段摘要 | 超过上下文时仍有价值；不能据此认定越多层压缩越好，旧模型和指标也不等于当前中文学习笔记的质量 |
| 滚动更新与分层合并有取舍 | [BooookScore，ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/f7b77476d89d5fb58aeb77691d2f40f5-Abstract-Conference.html) 比较两类图书摘要流程：滚动更新更细致，但连贯性评分更低 | 不建议把现有分块简单换成“不断重写一个总摘要”；需要保留可回查的结构化信息 |
| 长窗口不等于可靠理解 | [Lost in the Middle](https://arxiv.org/abs/2307.03172) 研究位置偏差；[NoLiMa，ICML 2025](https://arxiv.org/abs/2502.05167) 测试缺少字面匹配线索时的长上下文理解 | 主要是检索、问答任务，不能直接外推本模型的摘要成绩；提示我们测试中段信息和跨段推理 |
| 摘要本身也存在位置偏差 | [On Positional Bias of Faithfulness for Long-form Summarization，NAACL 2025](https://aclanthology.org/2025.naacl-long.442/) 直接研究长摘要及评估器的偏差 | 全文直读应作为基线，但仍要单独核验中间章节，不能只检查开头和结尾 |
| 语义切块不是通用升级 | [Is Semantic Chunking Worth the Computational Cost?](https://arxiv.org/abs/2410.13070) 在三类检索相关任务上未发现稳定、足以抵偿成本的收益 | 不宜先加入 embedding 切块再假定理解提高。这不否定“依据全文主题安排章节”；后者与向量检索的切块优化是不同问题 |
| 模型评分不等于事实验收 | [FABLES，COLM 2024](https://arxiv.org/abs/2404.01261) 的图书摘要人工评估发现，自动忠实度评估对错误声明的判断并不可靠 | 要检查具体声明和证据；同一模型的复核只能帮助发现问题，不能自行证明正确 |
| 可控工作流与按需取上下文 | Anthropic 的 [Building effective agents](https://www.anthropic.com/research/building-effective-agents) 和 [Context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) 强调简单可组合流程、结构化笔记和按需加载资料 | 借鉴明确阶段与少量回读工具，不因“Agent”而引入复杂框架或长时间自由循环。前一文章也提示其 2024 年工具生态已变化，本文只借鉴工作流原则 |
| 原文外置，按需检查 | [Recursive Language Models，2026-05 修订版](https://arxiv.org/html/2512.24601v3) 将长输入放在可访问环境中，允许模型检查和分解任务 | 借鉴可回读原文的思路；不照搬任意代码执行。论文也报告调用成本和时延的长尾，中文视频总结仍需单独验证 |

综合判断：真正要管理的是模型在每一步能够看到的资料，以及它丢弃了什么。更换分割函数、延长上下文、添加检索、增加反思轮数，单独使用都不能保证完整理解。

## 4. 社区经验如何使用

社区材料作为问题线索，不作为对我们模型的性能证明。

1. **长短视频不应共用相同细节预算。** BiliNote 用户在 [issue #221](https://github.com/JefferyHcool/BiliNote/issues/221) 反馈长视频笔记与短视频同样短，遗漏信息。该条是单个用户报告，创建于 2025-09-10，本次查询仍开放、无评论。我们应验证“概览可以短，完整笔记随知识密度增加”，不照搬其每百字总结的建议。
2. **切块应靠任务评测选择。** [r/Rag 的实践讨论](https://www.reddit.com/r/Rag/comments/1ov0pzk/i_tested_different_chunks_sizes_and_retrievers/) 报告不同长度、重叠和语义切块有取舍，评论还提出“小块找位置、大块供理解”。这是检索实验的个人经验，不能把其中的最佳长度或提升百分比移植到中文视频摘要。可借鉴的是命中一条字幕后返回所在段落及相邻语境。
3. **“Agent 能读大文件”与“忠实总结全文”不是同一验收任务。** [Hacker News 的 RLM-MCP 作者展示](https://news.ycombinator.com/item?id=46708942) 演示外置文件、程序筛选后返回结果，测的是日志查错。它支持一种实现可能性，不能证明对整段课程的理解和覆盖。我们的流程必须要求每个实质章节被阅读，不能只搜索几个关键词就宣告读完。

另外看了 [r/MachineLearning 关于摘要中间遗忘的讨论](https://www.reddit.com/r/MachineLearning/comments/1beb7vi/do_llms_get_lost_in_the_middle_during/)。讨论提出了问题和对照思路，但没有给出完成后的验证结果；这里不把它当结论，相关技术判断采用上面的摘要论文。

## 5. 适合现有模型的具体设计

以下是拟议方案，尚未实现。各阶段可以使用同一个 `deepseek-v4.1-flash`，无需另购模型、训练模型或先引入 Agent 框架。

### 5.1 无损原稿与阅读格式分开

原始字幕保持不变，作为引用和复核依据。在阅读层合并零碎字幕为自然段，保留段落编号到原字幕 ID、时间范围的完整映射。按标点、停顿和转场构造候选段落；任何规范化都保留原文，不靠模型记忆“纠正”专名和数字。

模型阅读紧凑的 `段落编号＋文本`。时间线、字幕编号范围和显示用时间戳主要由程序处理，需要推断时间关系时再提供必要时间信息。这样仍可从结论定位到视频，且不必反复传输冗长 JSON 字段。

### 5.2 依据预算选择短稿与长稿路径

区分三个值：**接口接受的上下文上限、经过评测的可靠阅读预算、一次回答的输出上限**。HTTP 请求体字节限制另算。我们目前没有这条平台模型路由经过验证的完整能力数据，不能按模型名称直接套用官方其他型号的 128K 等数字。

预算应覆盖：系统指令＋全文结构＋待读原文＋输出预留＋安全余量。推理 Tokens 如何计入输出上限，以该服务实际行为为准。有匹配 tokenizer 时使用它；没有时先保守估计，并用接口真实 usage 校准，不能将字符或 UTF-8 字节标成 Tokens。

| 路径 | 触发条件 | 执行方式 |
| --- | --- | --- |
| 短稿 | 原文和所需输出均在可靠预算内 | 一次整体阅读生成笔记及概览；程序检查来源，有疑点才定向复核，避免为了统一架构强制拆块 |
| 中长稿、全文可读 | 全文可放入可靠输入预算，但完整学习笔记需要较长输出 | 先全文建立结构；按主题生成完整章节；最终综合时保留原文回读能力。精简台词另设输出预算，不能把它挤进同一次过长回答 |
| 超长稿、全文不可读 | 超过可靠输入预算 | 顺序覆盖所有段落，提取主题、关键证据和关联候选；统合全文结构，再逐章深读。此时仍分批，但不把各块的短摘要作为唯一记忆 |

短稿不应为形式上的“全局规划”额外增加无价值调用。长短路径的边界通过样本实验决定，不先写死成“超过几分钟就是长文本”。

### 5.3 长稿先建立全文结构，而非立即生成最终摘要

让第一次阅读回答：视频想解决什么问题、论证怎么推进、哪些术语反复出现、哪些内容在后文被限定或更正。形成可验证的结构：

- 章节：标题、原文范围、要回答的问题；允许一个主题在多个位置再次出现。
- 术语：原文写法、缩写与别名、定义出现的位置；疑似转录错字保留不确定状态。
- 关系：前置概念、比较对象、因果链、例子与结论的对应关系。
- 更正：较早说法、后文限定／撤回、两处证据编号；矛盾不能仅按出现先后自动裁决。
- 未解决问题：指代不明、数字不清、依赖画面才能理解的代码或公式。

这份结构是辅助索引，同样可能出错，不能取代原稿。每章读到新证据时可以提出修订；修订需要依据并触发受影响部分重新生成，避免错误全局判断扩散到所有章节。

### 5.4 章节输出以可核对的关键声明为基础

每次读取“共享全文结构＋本章原文＋相关定义／更正段落”。按主题、论证和预算安排批次，保留自然边界；过长章节可以分次处理，过短章节可以一批处理。执行批次与用户看到的章节不是同一个概念。

在重要结论旁保存轻量证据记录：

| 字段 | 用途 |
| --- | --- |
| 声明、明确对象 | 避免压缩后“前者／后者”改变含义 |
| 条件、数值、单位、否定与限制 | 防止只留下结论，丢掉适用前提 |
| 作者归属、假说／传闻／观点等状态 | 区分视频作者说法与独立核实事实 |
| 支撑原文编号 | 允许回读，按需要附短原文证据；编号存在不等于证据支持该声明 |
| 相关声明、更正或冲突关系 | 保留非相邻章节的联系 |

这不是为每句口头语建立知识图谱。只对技术结论、数字、定义、关键论证和更正保留上述结构。用户看到的是连贯学习笔记，内部记录用于检查和恢复。

最终输出保留不同用途：**短概览、按知识结构组织的完整笔记、顺序精简台词、原稿**。长视频不会因为概览只允许几条要点，就丢弃正文细节。最终概览也不必将完整笔记机械地压成多层 200 字摘要；可读取结构与关键声明，疑难内容直接回到原文。

### 5.5 只在明确需要时回读，给 Agent 行为设边界

初期只需要三类操作：按编号读取原文范围、按词语／别名检索本视频、读取章节结构。没有可靠工具调用接口时，同样可以让模型输出受校验的 JSON 操作请求，由程序调度。

回读触发条件包括：比较对象不明、结尾出现撤回、相隔较远的章节描述同一概念、引用不支持结论、某个关键章节未进入完整笔记。检索命中后应返回完整段落及必要上下文，不能只给零碎关键词命中行。

建议先以最多两轮定向修订作为实验起点，并限制单任务请求数、Token 总量和时间。达到预算仍无法确认的内容显示“需回看”并附来源，不能通过不断重试制造确定性。这个轮数是待验证的产品控制值，不是论文给出的最优参数。

字幕始终是资料。字幕中的“忽略规则”“执行命令”等文字不会成为调度指令；回读限于当前任务的来源，引用 ID 由程序校验。该场景无需给模型任意 Python／Shell 执行能力。

### 5.6 恢复、用量和缓存规则继续保留

按原稿、阅读段落、全文结构、章节声明、验证结果、最终渲染保存阶段产物。检查点需要包含原稿哈希、模型路由、提示词与结构版本及依赖关系。修改全文结构时只让受影响结果失效；对完成且通过检查的阶段继续复用。

用量细分到规划、章节、综合、校验和重试。全局指令与稳定结构放在请求前缀，变化的章节资料放在后面，以便利用服务支持的前缀缓存。是否命中仍以 API 返回为准，不预估“必然命中”；本地检查点复用和服务端缓存是两个不同指标。

现阶段没有价格时比较输入／输出／推理／缓存 Tokens 和耗时；价格填写后按配置换算。频繁重写全文结构会使后续缓存和检查点失效，也应计入方案成本。

## 6. 暂不优先采用的方案

| 方案 | 暂缓理由 | 可能合适的时机 |
| --- | --- | --- |
| 只增大每块长度 | 是值得做的便宜基线，但不能单独解决跨章更正和证据核验 | 第一轮对照，隔离“切得太碎”的影响 |
| 单纯全文一次生成全部结果 | 输入能放下不代表详细输出能一次写完；中段遗漏仍需评估 | 短视频和简短概览 |
| embedding 语义切块作为核心升级 | 优化检索单元不等于建立全局理解，还增加模型和索引成本 | 后续检索确实因边界问题失败时 |
| 普通 Top-K RAG 直接生成整片总结 | 少量相关片段没有全文覆盖保证 | 用户就某个问题追问、定向复核 |
| 每块摘要不停更新同一个总摘要 | 易顺序依赖、反复改写和丢失早期细节 | 有证据记录支撑的流式处理，另行测评 |
| 完整 GraphRAG、多个 Agent 辩论 | 对当前单视频任务增加状态、成本和评估复杂度；收益未证实 | 跨视频课程库、实体关联与长期知识整理 |
| 无限制递归 RLM／自我反思 | 可能出现长尾调用；模型自主拆分也可能漏掉需要全面阅读的内容 | 受控研究分支，质量和预算都能独立评估后 |

## 7. 下一轮应如何验证

先冻结现有转录，隔离 ASR 差异；测试同一模型，不用换模型掩盖流程问题。原始视频画面才能给出的内容，本轮文本流程无法恢复，应作为来源限制标记。

### 对照组

| 组别 | 改动 | 回答的问题 |
| --- | --- | --- |
| A | 当前流程 | 保留真实基线 |
| B | 紧凑阅读格式＋合理输入／输出预算；能全文读时直接读，超限保持简单分组 | 仅消除碎片化和格式冗余有多少收益？ |
| C | B 加全文结构、主题章节、带来源的关键声明 | 全局语境是否改善关系和完整性？ |
| D | C 加双向核验和有预算的原文回读 | 额外校验是否值得增加的 Token 和耗时？ |

相同来源、相同输出类型、相近的最终笔记长度预算。记录模型 ID、提示词版本、采样／推理配置；固定能够控制的参数。先做小样本，再扩大长视频评估。不能仅凭 D 比 A 好，就将全部收益归因于 Agent 校验。

### 样本与检查项

- 现有约 7 分钟新闻：作者归属、预测与事实区分、相近产品名、跨字幕主语。平台字幕与 ASR 分开比较，不混为同一输入。
- 55 分钟历史样本：叙事关联、传说限定、后文更正；只验是否忠实于来源，不把视频内容当作医学／历史真实性标准。
- 87 分钟技术样本：定义、公式中的对象与条件、步骤顺序、参数和单位、结尾对前文的补充。优先复核既往“前者／后者”问题。
- 加入明确标记为合成的短回归材料：前面结论后面撤回、同名不同对象、单位变化、否定、相隔多段的定义、需要看画面的公式、字幕中夹带指令。不得把合成材料混入真实任务或引用。

每个长视频先建立约 20–30 条有原文依据的关键事实／关系清单，分布在开头、中段和结尾，包含跨章关系。清单只是小型验收集，不代表逐字全量标注。结构化程序检查与模型辅助检查之外，关键数字、更正和复杂关系要人工复核；不能用生成模型自己的满意评分代替。

| 指标 | 检查方式 |
| --- | --- |
| 重要内容覆盖 | 按预先确定的重要程度核对清单，检查完整笔记；概览另看代表性，不要求塞入所有细节 |
| 忠实度 | 将核心输出拆成可核验声明，检查对象、前提、否定、单位、作者归属；找无依据的添加 |
| 关系与更正 | 单独计数跨章联系、比较方向、最终撤回是否处理正确 |
| 引用有效性与精确性 | 编号／范围有效由程序检查；支撑关系和定位是否过宽另查 |
| 结构与可读性 | 主题是否连贯、同一内容是否重复、是否出现未完句；遮住方案标签比较 |
| 效率 | 总请求数、各阶段 Tokens、真实缓存命中、端到端时间；多次运行后才能谈稳定的长尾表现 |
| 恢复 | 在全文结构、章节和核验阶段分别中断，验证已完成结果不重新付费生成，依赖变更能正确失效 |

建议的上线门槛：关键数字和比较方向无已知新增错误；已明确撤回的说法不作为最终事实；引用合法且能支持核心结论；重要内容覆盖不低于基线；质量提升的额外成本可解释。无法判断的项目保留疑点，不以“原稿 ID 100% 覆盖”宣称语义零遗漏。

## 8. 本轮产出与下一步范围

本轮完成论文／官方资料、三个开源项目实现、产品交互和社区反馈的交叉调研，以及四份本地原稿的离线规模审计。产物为本文与审计 JSON；生产总结代码未修改，没有产生新方案的付费模型调用。
