## 已确认需求

- 产品为独立 macOS 应用；暂不以跨平台为目标。
- 输入 Bilibili 视频链接，获取可处理的媒体内容。
- 包含需要用户登录后才能访问的内容；具体内容类型和下载可用性需要实际样本验证。
- 提供媒体保留选项：保存在本地，或处理后清理。
- 提供原始台词文本、精简台词和合理的结构化总结。
- 初步路线为本地 Whisper 转录，加远程大语言模型整理。
- 以中文为主，题材广泛，科技知识、代码编程和人工智能科研类居多。
- 通常时长在 30 分钟内，最长预计约 90 分钟。以此选择验收样本，不把 90 分钟写成未经讨论的强制拒绝阈值。
- 默认优先使用已有字幕；没有可用字幕时使用本地 Whisper，并提供手动切换入口。
- 默认输出选择学习笔记，重视理解和技术细节；同时保留原稿和精简台词。
- 用户提供积算平台 API，已明确模型标识为 `deepseek-v4.1-flash`（替代最初的暂记名称）。采用 OpenAI 兼容 Chat Completions 协议，Base URL 为 `https://api.icompify.com/v1`。不能据模型名称推断上下文长度或价格。
- 长视频必须有明确的文本分块与汇总方案。
- 第一阶段不做关键帧截图；界面、性能和其他能力分阶段扩展。
- 最近任务支持用户自建项目、任务归属和未归属视图，参考会话管理的组织方式。
- 增加常用设置、独立模型管理页面和用量 / 费用统计；参考主流开源项目的服务商与模型管理方式。
- 积算平台单价暂时未知，先实现可编辑价格表，不预填其他服务商价格。
- 新版总结使用紧凑输入、短稿整体阅读、长稿全文结构与定向回读；保留旧流程作对照，以现有短视频和两个长视频检查质量、遗漏、耗时、用量与恢复。

## 建议的第一版体验

1. 粘贴链接，显示标题、作者、时长；多 P 视频明确选择要处理的一 P，避免自动下载整个合集。
2. 选择文本来源策略和“保留媒体 / 完成后删除媒体”。
3. 开始处理，按解析、下载、转录、整理、汇总显示阶段和真实进度。
4. 分别查看原始转录、精简台词、结构化总结；保留时间戳，支持返回原视频核对。
5. 导出 Markdown、TXT 和 SRT，并在历史任务中重新打开结果。
6. 失败时显示具体阶段，保留已经完成的结果；更换 API 或重试总结不要求重新下载和转录。

这些是建议的实现默认值，尚不是已验证功能。

## 三类文本的区别

| 产物 | 内容 | 编辑原则 |
| --- | --- | --- |
| 原始转录 / 来源字幕 | 按时间排列的原始文本与来源标记 | 不被大模型整理结果覆盖；机器识别不能保证逐字准确 |
| 精简台词 | 顺着原视频顺序去掉口头语、重复和无关插话 | 保留论证、数字、限定条件、例子和结论，不只剩摘要 |
| 结构化总结 | 概览、章节、核心观点、关键细节和结论 | 观点附来源时间，区别说话者观点与确定事实，不补写视频未提供的内容 |

第一阶段以视频内容整理为目标。外部知识补充或联网事实核查作为后续独立功能，避免和视频原意混在一起。

科技、编程和科研内容优先保留技术名词、数字、版本、实验条件、论证过程、关键步骤及限制。无法由来源确定的专业词不凭空改成另一个看似合理的名称。第一阶段不读取画面中未被讲述的代码、公式和图表。

## 字幕优先策略

- 解析视频信息后检查可用字幕轨，优先选择中文；明确标记字幕语言和来源。只有平台提供足够元信息时才区分人工字幕与自动字幕，不靠语言名猜测。
- 统一保留每段的起止时间和原始文本，供原稿展示、分块和导出使用。
- 无字幕、字幕为空或格式无效时进入本地转录；登录失效与网络失败应先说明原因，不能伪装成“没有字幕”。
- 用户可以强制使用本地转录。重新生成的文本保存为独立来源，不覆盖已保存的平台字幕。
- 切换文本来源后，旧的精简稿和总结仍标注原来源，需要基于新来源重新生成，避免混淆。
- 拟提供人工字幕、平台自动字幕、本地 Whisper 三种来源标签；实际无法确定的来源只标“平台字幕”。

## 长视频方案

不把全部文本一次性塞入模型，也不先引入自主 Agent 框架。采用可记录、可重试的固定工作流：

1. 转录段保存唯一 ID、起止时间和文本。较长音频采用有界内存处理，并保留已完成片段；切片边缘要处理重复与断句。
2. 按句子和语义边界组织文本块。由实际 API 的上下文和输出限制决定预算，扣除提示词、输出空间与安全余量，不把中文字符数直接当作 token 数。
3. 每块生成精简稿和带来源 ID 的结构化笔记。少量相邻上下文只用于理解，输出归属明确，避免重复。
4. 全文精简稿由各块整理稿按原顺序合并。全文总结由分块笔记综合生成，不能用一份短摘要替代所有正文。
5. 若分块笔记仍然超限，继续分层合并，并保留章节笔记供阅读。汇总必然压缩信息，因此原始转录始终可查。
6. 检查片段覆盖、输出是否被截断、结构是否有效、引用的来源 ID 是否存在。验证失败时重试或进一步拆块。
7. 每阶段持久化。网络中断、限流和上下文超限分别处理；不无限重试，不静默丢弃超长内容。

后续如需要“向视频提问”，再增加检索和引用机制；它不是第一版总结流程的前置依赖。

## 技术方案建议

| 层次 | 首选候选 | 原因与验证点 |
| --- | --- | --- |
| 界面 | SwiftUI 原生 macOS 应用 | 符合独立应用要求，便于接入文件、Keychain 和系统窗口 |
| 视频获取 | yt-dlp | 有现成 Bilibili 提取器和登录会话支持；用真实链接验证可用性 |
| 媒体处理 | FFmpeg | 提取音轨、规范音频格式；不为纯语音识别无谓提高视频清晰度 |
| 本地转录 | 优先验证 WhisperKit，MLX Whisper 作为候选 | 两者都有 Apple 平台实现；以中文样本准确度、耗时、峰值内存和打包难度选型 |
| 大模型 | 可替换的 API 适配层 | Base URL、模型名和能力配置独立于业务；是否兼容 OpenAI 接口需要服务商文档确认 |
| 任务和数据 | 本地任务记录、原子写入的阶段产物 | 支持恢复、单阶段重跑和可控清理；底层存储方案在实现时确定 |

不以功能数量决定转录引擎。先选一个引擎跑通并测量，不在第一版同时维护多套完整推理后端。

独立应用最终应能从 Finder 启动。早期内部验证可使用本机已有工具；面向其他 Mac 的可分发安装包还需处理依赖、模型下载、签名和系统兼容性，不把“本机能运行”视为完成分发。

## 登录、设置与数据流

- 登录由用户在本机完成。优先验证应用内网页登录或显式导入已有登录会话的可行性；不收集聊天中的账号密码。
- 不自动读取用户浏览器的所有会话。登录失效时提供重新登录入口；账号可播放不代表下载器一定支持，需要给出准确的失败原因。
- 正式应用建议通过设置界面输入 API 密钥并保存到 macOS Keychain。早期开发配置保存在权限为 0600、由 `.gitignore` 排除的本机 `.env`，不在文档或日志中记录其值。已通过此配置完成一次模型列表读取和一次小文本测试；当前字幕预览 UI 尚未接入模型。
- 发送给模型的是必要的文本、时间标记及标题等上下文。媒体文件和登录会话不作为总结请求内容发送。
- 下载内容放在应用管理的任务目录；清理只针对本任务创建的媒体和中间文件。
- “完成后清理”建议在文字产物成功落盘后执行；失败或取消时保留恢复所需数据并提供清理入口。
- 原始转录、精简稿、总结与媒体保留策略分开管理。删除视频不应同时删除文字结果。
- 如果用户选择不保留视频且只需语音内容，可考虑仅获取音轨；是否采用这一优化待媒体使用方式明确后决定。
