# 开发记录

## 从链接到学习笔记

产品最初面向 macOS 中文视频学习，常见视频不超过30分钟，按约90分钟目标设计。首先交付三份可保存文字：原稿、精简台词和学习笔记。关键帧、画面公式识别留作后续；0.7.0 开发预览开始增加独立的手机录音对话整理功能。

SwiftUI 提供原生界面，yt-dlp / FFmpeg 负责获取媒体。先检查已有 Whisper 环境，再接入 MLX / Metal 单一推理后端，复用权重而非重复下载。平台字幕优先，并可手动切换。

## 2026-10-25：端到端与长视频

0.2 跑通真实字幕、720p H.264 MP4、AI 整理、媒体保留和重启读取。0.3 增加项目管理，用55:43历史讲解与87:05技术精读验证转录和取消恢复。

转录窗口靠近停顿、保留上下文，再按词时间确定归属。原稿不被总结覆盖，窗口原子保存，恢复时核对哈希与修改时间。相邻文本块出现未完句或重复时，合并接缝并继承来源。

真实问题之一是“前者 / 后者”在压缩后改变顺序，导致复杂度比较颠倒。由此明确：来源合法只证明可追溯，不证明语义正确；对象、条件和后文更正需要核验。

## 2026-10-25：全文理解与回读

调研后保留旧流程作基线，引入紧凑输入、短稿整读与长稿全文结构。自然章节组织知识，执行预算限制请求大小。核验访问原文，跨章声明带齐来源；回读解决指定问题，避免无限循环。

最终二进制检查还发现上游 NumPy / Swift 工具链留下了 Homebrew 与 CLT 的运行时搜索路径；签名前移除这些构建机路径，并增加逐文件检查，防止打包环境掩盖可重定位问题。

本机没有 Developer ID，按发布选择使用 ad-hoc 签名并明确标为“未公证”。不以本机启动成功代替 Gatekeeper / Apple 公证结论。检查和已知限制见 [0.6 验收](validation-0.6.md)。

## 2026-10-28：0.7.0 录音工作区与思考强度（开发预览）

本轮在 `codex/recording-workspace` 上开发，承接尚未合并的任务管理分支；没有直接在 `main` 开发。目标是普通话、通常 5～50 分钟的二人录音：保留原话，忠实梳理双方观点、问答与共识。当前 GitHub 二进制仍为 0.6.0，0.7.0 仅在维护者本机作为构建 9 预览使用，尚未合并或发布。

用户确认两个功能页各自维护资料库，因此左上角菜单切换整个 B 站或录音工作区，项目、最近、未归属和归档分别保存。磁盘也分为视频 `tasks/` 与录音 `recording-tasks/`，防止较旧应用回退后将录音当成视频读取。旧视频任务缺少来源字段时仍归入 B 站；跨功能页移动、归档和删除需校验归属。模型服务与计费设置继续共用，本轮用量来源筛选也按视频、录音和连接测试区分。

录音导入保存任务副本，外部原件保留。MLX Whisper 沿用 Metal 转录和窗口检查点，录音路径另外保留词时间用于对齐；视频任务既有转录检查点身份不改。SpeakerKit 作为可关闭的二人分离组件，整段分人后对齐词时间；模糊与重叠区域保留未确定归属，不根据文字猜说话人。计算路径为语音分割 CPU、声纹嵌入 CPU / Neural Engine、聚类 CPU，不能统称全 GPU 加速；来源与模型说明见[组件清单](../packaging/speakerkit.json)。

实现上分开机器 ASR、自动分人原稿、人工修订和显示名称。姓名变化只是展示变化；文字或话轮归属变化则改变总结依据，不能沿用旧总结检查点。分人失败保留已完成 ASR，重试重跑未完成的整段分人；没有依赖组件未承诺的内部断点。Whisper 完成后释放本进程模型缓存，再进入分人，避免两个模型无谓重叠占用内存。

本地处理与模型调用明确分成两步。先转录、回听与校订，再由用户点击“整理与总结”。总结复用全文结构、来源核验与有界回读，但采用对话规则并保留稳定说话人标记，重点避免把建议写成承诺、把疑问写成主张、把条件句写成已决定事项。

模型配置增加逐模型思考强度。原有 `low` 保留；默认档省略参数，DeepSeek V4 显示 low / high / max，通用接口可另选 medium。连接成功只说明服务端接受请求，不能证明代理实际执行对应强度。请求记录保存选择值，实际用量以平台返回为准；不把更高强度宣传为自动提升质量。

本轮 80 项 Python / 66 项 Swift 离线测试通过。5 分钟合成普通话录音完整本地处理 40.14 秒；50 分钟真实 WAV 在首窗后取消并恢复，合计 342.581 秒，实际复用 1 窗、新算 12 窗，完成后重复请求复用阶段且检查点内容和修改时间保持不变。Whisper 确认使用 Metal；说话人分析保持混合计算路径。合成样本只能用于复现流程、资源和恢复行为，不可替代真实两人录音的准确率和长对话质量验收。

真实 API 共 6 次，输入 7028、输出 26339 Tokens，推理量已包含在输出内。人为压低输出预算的测试暴露了“推理用完额度却没有正文，随后继续拆分重试”的浪费路径：现在明确停止，保存失败类型与用量，不继续自动拆分。正常 12288 上限的 whole 返回完整 JSON，一处引用未排序；只排序引用后离线结构检查通过，没有手改正文。该次未运行完整 review，不能算作默认总结流程全部通过。

人工核对还发现概览将单方所谓共识升级为双方认可、正文泄露内部来源编号、裸 A / B 不符合稳定标签约定，因此加强提示词中的双方证据、标题和正文标签规则；这些提示词改进尚未再次真实调用验证。界面修复及实测同时覆盖说话人改名联动到标题、正文与导出，单句校订令旧总结过期并禁用过期导出，整页资料库切换、同名项目隔离、导入副本、回听、归档恢复、思考强度保存和用量来源筛选。

构建增加独立 `--output-dir`，本地自包含预览在候选目录制作，保留 `dist/` 中正式发行产物；SpeakerKit helper 随应用构建、签名和携带组件声明。自包含候选已通过包内95秒录音、签名和运行依赖检查；安装副本启动、旧任务读取、正常退出及重开通过，设置与项目目录指纹不变。单份应用已更新至0.7.0/构建9，上一版0.6.1的压缩回退包完成轮换；临时应用副本已清理。代码通过PR等待确认，正式Release未变。完整证据和剩余限制见[录音预览验收](validation-recording-preview.md)，用户步骤见[录音整理指南](recordings.md)。

## 2026-10-28：真实手机录音、计量核对与高强度预算

使用用户提供的21分42秒普通话M4A，在应用任务目录保存副本，原微信文件不变。Whisper确认使用Metal，主动在首窗后中断，再恢复本地转录、说话人分析和对齐，累计286.859秒（含首次分人模型下载）；完成后重放0.507秒，检查点内容和修改时间不变。ASR的784段对齐为1060段，除去5个空格外没有文本损失；10.05%的文字说话人未确定，没有人工音频参考，不能把这一比例解释成错误率。

真实调用暴露了三类问题：长核验超过150秒时客户端过早退出；只返回思考但无正文时预算不足；整理稿会把碎片原话扩写成解释旁白。修复后较大请求延长等待、超时不自动重提，已完成阶段继续复用；对话提示词保持直接原话与人称，保存的Markdown标题也同步应用说话人显示名称。未返回的用量保持未知，未配置或缺少计价依据的费用不当作零。

低强度对照完整完成13章、59条章节要点、8条关键点和15条待确认；核验覆盖全部504个紧凑段落，6次定向回读累计修正9处。完成后1.026秒重放，零新请求、检查点未改变。首次运行与恢复合计1539.458秒，包含一次超时，不能把恢复段的815.248秒当成全新任务的总耗时。整理对话仍比原稿略长，专名、简短应答和部分归属仍需回听，不宣称语义零遗漏。

用户提供的后台账单与恢复阶段11条请求一一对应。未缓存输入40429、缓存28992、输出62338 Tokens，以输入2元、缓存0.04元、输出8元每百万Tokens核算为0.58072168元，与平台完全一致。排除其他应用请求；本地输入总量包含缓存，推理包含在输出内，不重复计费。

高强度先前在中段核验耗尽16K与32K预算仍没有正文。用户要求继续探索更高预算后，将核验上限扩展到128K，并保留已知失败预算与成功检查点；较大回答最多等待30分钟，高强度整轮上限2小时和100万已返回Tokens，仍受80次请求限制。128K实测在该阶段成功返回正文，实际输出22504，其中推理22107，耗时331.834秒。之前32K耗尽、本次不到32K完成，表明输出量有波动；这只证明本次128K配置可用，不能据此断言固定最低额度。

本轮87项Python与66项Swift检查通过；真实模型请求、原始录音、原稿与报告留在被忽略的本机目录，公开文档只记录聚合结果。高强度最终完整完成11章、59条章节要点、8条关键点及19条待确认；1060.432秒恢复后再执行1.032秒，零新请求。高强度仍有含混词过度解释和疑点重复，不能仅以预算或改动数量判断质量。

本机更新到0.7.0构建14，代码源988c390；旧视频任务、真实录音总结及用量页读取正常，偏好与视频资料库指纹不变，正常退出与重开通过。轮换一份构建10的压缩回退包并清理临时应用；代码通过PR继续等待确认，未合并或发布Release。完整结果、安装与剩余限制见[录音预览验收](validation-recording-preview.md)。

## 2026-10-29：会议纪要工作流预览

在冻结 `context-v2` 代码与结果后新增 `meeting-baseline` 和 `meeting-v3`。同一份完整原稿先生成详细纪要，另一个不含草稿的请求提取重要证据，再对照原文提交具体修订；确定性程序校验目标、来源、状态和字段后应用，保留前后版本。问题按目标与字段定位，最多两轮六项回读，不再按每六个阅读单元固定重读全文。超过实际输入预算才拆分完整责任范围，后续更正移动引用位置也不重新分派审查。
